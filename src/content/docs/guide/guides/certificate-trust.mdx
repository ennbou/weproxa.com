To intercept HTTPS traffic on macOS, WePROXA generates a local root Certificate Authority (CA) and trusts it in macOS Keychain. This lets WePROXA decrypt, inspect, and re-encrypt HTTPS traffic for the hosts or apps you explicitly enable.

This page covers macOS. For the other platforms, see [Windows HTTPS Certificate Setup](/guide/guides/windows-https-certificate-setup/) and [Linux HTTPS Certificate Setup](/guide/guides/linux-https-certificate-setup/).

## Setup Process

When WePROXA starts, it automatically generates a root CA certificate unique to your machine. To intercept HTTPS traffic, you must install and trust this certificate.

<Steps>

1. Open WePROXA and go to **Settings** → **CA Certificate**.
2. Click **Install to macOS**.
3. Enter your macOS password when prompted. The certificate is installed in the System keychain and marked as trusted for SSL/TLS connections.

</Steps>

![WePROXA CA Certificate settings](@assets/generated/screenshots/settings/certificate.png)

After this one-time setup, HTTPS interception works seamlessly.

## Recognizing Your WePROXA CA

Newly generated certificates keep the **WePROXA Root CA** prefix and add the UTC generation date, your computer's hostname, and a short serial suffix. For example:

```text
WePROXA Root CA (23 Feb 2026, developer-mac.local, 96DEBEFB)
```

The date is the day WePROXA made the certificate. **Settings** → **CA Certificate** shows **Valid from** instead, which is two days earlier, so devices whose clock runs a little behind still accept the certificate.

The extra identity helps distinguish certificates created on different computers or after regeneration. The short suffix comes from the certificate's serial number. Certificates generated by older WePROXA versions may still appear simply as **WePROXA Root CA** and continue to work until you regenerate them.

## Trust Status

The **Certificates** settings show a live **Trust status** for the local CA so you always know whether HTTPS can be decrypted:

- **Installed & trusted** — the certificate is in Keychain and set to trust SSL/TLS. Interception is ready.
- **Not trusted yet** — the certificate exists but is not installed or trusted. Install it to inspect HTTPS.
- **Set to "Never Trust"** — the certificate is explicitly distrusted in Keychain, which blocks interception until you re-enable trust.

If SSL interception is enabled while the certificate is not trusted, WePROXA warns you that HTTPS won't be decrypted until you install it.

### Guided Setup

When the certificate still needs attention, WePROXA can walk you through fixing it instead of sending you to Keychain unaided:

- If it is **not trusted yet**, an **Install & Trust** action installs and trusts the certificate in one step.
- If it is **set to "Never Trust"**, the dialog explains how to switch it back to **Always Trust** in Keychain Access.

You can reopen these steps at any time from the certificate menu or the **Certificate settings** link.

## Manual Trust

If you need to manually trust the certificate:

1. Open **Keychain Access** from Spotlight.
2. Find the **WePROXA Root CA** certificate in the **System** keychain, or in the **login** keychain if it was installed for the current user only.
3. Double-click it and expand **Trust**.
4. Set **Secure Sockets Layer (SSL)** to **Always Trust**.
5. Close the window and enter your password to confirm.

## Managing the Certificate Lifecycle

The **Certificate lifecycle** controls in **Settings** → **CA Certificate** let you manage the local CA directly from WePROXA:

- **Generate certificate** — create a new local CA when none exists yet.
- **Regenerate certificate** — replace the CA identity and private key. HTTPS inspection stops working until the new certificate is installed and trusted again on every device.
- **Download certificate** — save the CA certificate to a file, for example to trust it on another device.
- **Remove local certificate** — permanently delete WePROXA's local CA certificate and private key.

:::caution
Stop the proxy before regenerating or removing the certificate. Regenerating creates a brand-new CA identity, so any copies already installed in Keychain or on other devices keep pointing at the old certificate until you remove and reinstall them there.
:::

## Removing the Certificate

The quickest way to remove the CA is the **Remove local certificate** action described above. To also delete copies from Keychain (or to remove a certificate installed by an older version):

1. Open **Keychain Access**.
2. Search for **WePROXA**.
3. Right-click the certificate and select **Delete**.

## CI Jobs and Headless Runs

`weproxa-cli headless` does not use the app's CA or the macOS Keychain. By default, each run makes its own CA, and it never asks to install it. Two ways to trust it:

- **Tools in the same job.** `weproxa-cli env` prints `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, and similar variables that point each tool at the run's CA. Nothing is installed, and no step needs `sudo`.
- **Clients built ahead of time.** An iOS Simulator snapshot, an Android debug build, or a container image must trust the CA before the run starts. Make a CA once with `weproxa-cli ca create`, trust it there, and pass it to every run with `--ca-cert` and `--ca-key`. Use `--only-hosts` so the CA can sign only for the hosts you test.

Chrome and Chromium ignore both. They take the CA's key hash with `--ignore-certificate-errors-spki-list`. See [Headless CLI](/guide/guides/headless-cli/#use-a-ca-you-keep) for the commands.

## Security

- The CA certificate is generated locally and never leaves your machine
- The private key is stored securely in the app's data directory
- Each installation generates a unique certificate
- Removing WePROXA also removes the ability to impersonate any site
